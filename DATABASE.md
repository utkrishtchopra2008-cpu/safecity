## 1. Purpose and Scope

This document defines the authoritative database model for SafeCity AI's MVP. It specifies the tables, columns, relationships, constraints, indexes, authorization boundaries, migration strategy, seed data, and recovery requirements.

The schema supports:

- Authorized application users and server-managed sessions.
- Video or simulated sources.
- Normalized incident detections.
- Evidence metadata and incident-to-evidence associations.
- Video-quality and evidence-sufficiency assessments.
- Human review outcomes.
- Background video-processing jobs.
- Versioned evaluation datasets and ground-truth events.
- Evaluation runs and measurable reliability results.

The database must preserve the distinction between a model prediction, a reliability assessment, a human review, and an evaluation result.

Do not add tables for billing, organizations, notifications, face identities, cross-camera tracking, or other capabilities excluded from the PRD.

## 2. Database Technology

### 2.1 Recommended Technology

Use **PostgreSQL** as the single authoritative relational database.

Reasons:

- Transactional consistency for incident ingestion and review submission.
- Foreign keys and constraints for reliable relationships.
- Indexes that support incident lists, processing queues, and evaluations.
- JSONB for limited, schema-validated assessment metadata where structure legitimately varies.
- A straightforward integration with SQLAlchemy and Alembic.
- Support for future row-level security if an approved multi-tenant requirement emerges.

Use SQLAlchemy 2 for application database access, Psycopg 3 as the PostgreSQL driver, and Alembic for migrations, as specified in ARCHITECTURE.md.

### 2.2 General Conventions

- Primary keys use UUIDs, generated by the application or a supported PostgreSQL UUID default.
- Timestamps use PostgreSQL TIMESTAMPTZ and are stored in UTC. Display timezone conversion belongs to the application.
- Monetary types are not needed for the MVP.
- Use explicit foreign keys and stable, constrained status values.
- Use TEXT or VARCHAR with CHECK constraints for status values rather than introducing PostgreSQL enum types prematurely.
- Use JSONB only for supplementary metadata that genuinely varies. Frequently filtered values must have typed columns.
- Use numeric types for metric outputs when reproducibility matters; avoid relying on binary floating-point persistence for reported metrics.
- All timestamps needed to reconstruct processing and review history must be stored explicitly.
- The application must not store large video binaries in PostgreSQL. Store evidence in private file or object storage and persist metadata and storage keys in the database.

### 2.3 Types Used in This Specification

| Type | Meaning |
|---|---|
| UUID | 128-bit identifier |
| VARCHAR(n) | Bounded text |
| TEXT | Unbounded text |
| BOOLEAN | True or false |
| INTEGER | Whole number |
| BIGINT | Large whole number, such as bytes |
| NUMERIC(p,s) | Exact decimal with defined precision and scale |
| TIMESTAMPTZ | Timezone-aware timestamp |
| JSONB | PostgreSQL binary JSON |
| CHAR(n) | Fixed-length text |
| TEXT[] | PostgreSQL text array, if used by the implementation |

Unless explicitly marked nullable, a field described as required is NOT NULL. Defaults are implementation defaults, not a substitute for request validation.

## 4. Tables and Columns

### 4.1 users

Stores application identities and their authorization role.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| email | VARCHAR(320) | No | Login email; store normalized lowercase value |
| display_name | VARCHAR(120) | No | Display name |
| password_hash | VARCHAR(255) | No | Password hash only; never store the raw password |
| role | VARCHAR(32) | No | CHECK: operator, supervisor, technical_admin |
| is_active | BOOLEAN | No | Default TRUE; deactivation prevents new sessions |
| created_at | TIMESTAMPTZ | No | Default current timestamp |
| updated_at | TIMESTAMPTZ | No | Update on changes |

**Constraints**

- Primary key: id.
- Unique: email.
- Require email to be stored normalized to lowercase; validate syntax in the application.
- CHECK role is one of the supported values.
- Prefer deactivating accounts over deleting them because review history must retain reviewer attribution.

### 4.2 sessions

Stores server-managed login sessions. Only a token hash is persisted.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| user_id | UUID | No | FK to users.id |
| token_hash | CHAR(64) | No | Unique hexadecimal hash of a high-entropy session token |
| created_at | TIMESTAMPTZ | No | Session creation time |
| expires_at | TIMESTAMPTZ | No | Expiration time |
| last_seen_at | TIMESTAMPTZ | Yes | Last activity, if tracked |
| revoked_at | TIMESTAMPTZ | Yes | Set when logged out or revoked |

**Constraints**

- Foreign key: user_id references users.id with deletion restricted.
- Unique: token_hash.
- CHECK expires_at > created_at.
- A session is valid only if it has not expired, has not been revoked, and its user remains active.

### 4.3 sources

Represents a configured source that can produce candidate detections. For the MVP, source types are uploaded clips and simulated sources.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| name | VARCHAR(160) | No | Operator-facing source name |
| source_type | VARCHAR(32) | No | CHECK: uploaded_clip, simulated |
| status | VARCHAR(32) | No | CHECK: ready, processing, unavailable, failed, disabled |
| configuration | JSONB | No | Default empty object; non-secret source settings only |
| created_by | UUID | Yes | FK to users.id |
| last_processed_at | TIMESTAMPTZ | Yes | Most recent successful processing time |
| created_at | TIMESTAMPTZ | No | Default current timestamp |
| updated_at | TIMESTAMPTZ | No | Update on changes |

**Constraints**

- Foreign key: created_by references users.id with ON DELETE SET NULL.
- CHECK configuration is a JSON object.
- Secrets and credentials must not be stored in configuration JSON.
- Sources referenced by incidents or evidence should be disabled or archived through status changes rather than hard-deleted.

### 4.4 evaluation_datasets

Stores metadata for a versioned evaluation dataset and its ground-truth annotations.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| name | VARCHAR(160) | No | Dataset name |
| version | VARCHAR(80) | No | Immutable dataset version identifier |
| description | TEXT | Yes | Brief description |
| provenance | TEXT | No | Origin and annotation provenance |
| license_identifier | VARCHAR(160) | Yes | License or data-use identifier |
| permitted_use | TEXT | No | Documented permitted use and constraints |
| annotation_format | VARCHAR(80) | No | Annotation format/version |
| status | VARCHAR(24) | No | CHECK: draft, ready, archived |
| created_by | UUID | Yes | FK to users.id |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign key: created_by references users.id with ON DELETE SET NULL.
- Unique: (name, version).
- A dataset marked ready must have the required assets and valid annotation coverage for the intended evaluation.
- Dataset versions should be treated as immutable after use in a completed evaluation. Corrections should produce a new version.

### 4.5 processing_jobs

Tracks long-running source-processing and evaluation jobs. PostgreSQL is the MVP job queue and source of truth for job status.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| job_type | VARCHAR(32) | No | CHECK: source_processing, evaluation |
| status | VARCHAR(24) | No | CHECK: pending, running, completed, failed |
| source_id | UUID | Yes | FK to sources.id for source-processing jobs |
| dataset_id | UUID | Yes | FK to evaluation_datasets.id for evaluation jobs |
| created_by | UUID | Yes | FK to users.id |
| attempt_count | INTEGER | No | Default 0; nonnegative |
| max_attempts | INTEGER | No | Default 3; positive |
| available_at | TIMESTAMPTZ | No | When the job may be claimed; default current timestamp |
| started_at | TIMESTAMPTZ | Yes | First/current execution start time |
| heartbeat_at | TIMESTAMPTZ | Yes | Latest worker heartbeat |
| lease_expires_at | TIMESTAMPTZ | Yes | End of current worker claim, when a lease is used |
| finished_at | TIMESTAMPTZ | Yes | Completion or final failure time |
| error_code | VARCHAR(80) | Yes | Safe, machine-readable failure code |
| error_summary | VARCHAR(500) | Yes | Sanitized summary; no secrets or private paths |
| result_metadata | JSONB | No | Default empty object; non-sensitive summary only |
| created_at | TIMESTAMPTZ | No | Default current timestamp |
| updated_at | TIMESTAMPTZ | No | Update on changes |

**Constraints**

- Foreign keys: source_id references sources.id; dataset_id references evaluation_datasets.id; created_by references users.id. Deletion of referenced operational records should be restricted or handled through deactivation.
- CHECK attempt_count >= 0 and max_attempts > 0.
- CHECK result_metadata is a JSON object.
- CHECK job target consistency:
  - source_processing requires source_id and forbids dataset_id;
  - evaluation requires dataset_id and forbids source_id.
- A completed job must have finished_at.
- A worker must not mark a job completed until required output rows are committed.
- Do not store raw exception dumps, session data, or sensitive media metadata in error_summary or result_metadata.

### 4.6 incidents

Stores normalized candidate detections. The original prediction is retained independently of the current human-review status.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| source_id | UUID | No | FK to sources.id |
| processing_job_id | UUID | Yes | FK to processing_jobs.id that generated the result |
| source_event_id | VARCHAR(200) | Yes | Stable event ID supplied by the source/detector, if available |
| event_start_at | TIMESTAMPTZ | Yes | Event start time from the source |
| event_end_at | TIMESTAMPTZ | Yes | Event end time, if known |
| received_at | TIMESTAMPTZ | No | When the application ingested the detection |
| detection_category | VARCHAR(120) | No | Normalized candidate event category |
| detector_name | VARCHAR(160) | No | Detector implementation identifier |
| detector_version | VARCHAR(120) | Yes | Model/code version |
| detector_label | VARCHAR(160) | Yes | Original detector label, when distinct from normalized category |
| detector_score | NUMERIC(20,10) | Yes | Original numeric score |
| score_semantics | VARCHAR(160) | Yes | Meaning of the score, e.g. anomaly score or confidence output |
| review_status | VARCHAR(24) | No | CHECK: unreviewed, reviewed; default unreviewed |
| created_at | TIMESTAMPTZ | No | Default current timestamp |
| updated_at | TIMESTAMPTZ | No | Update on changes |

**Constraints**

- Foreign keys: source_id references sources.id; processing_job_id references processing_jobs.id.
- CHECK event_end_at is NULL or event_start_at is NULL or event_end_at >= event_start_at.
- CHECK review_status is unreviewed or reviewed.
- Partial unique index on (source_id, source_event_id) when source_event_id is not NULL.
- The original detector label, score, score semantics, detector name, and version must not be overwritten by a review.
- A detector score is not assumed to be a probability and must not be constrained to 0–1 unless the selected detector's documented semantics require that constraint.
- Incident creation and associated assessment/evidence linkage should be performed transactionally where practical.

### 4.7 evidence

Stores metadata and storage references for original video, extracted clips, or image frames. The actual media bytes remain outside PostgreSQL.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| source_id | UUID | No | FK to sources.id |
| evidence_type | VARCHAR(24) | No | CHECK: original_video, clip, frame |
| storage_backend | VARCHAR(24) | No | CHECK: local, object |
| storage_key | TEXT | No | Internal key, never a user-controlled filesystem path |
| mime_type | VARCHAR(120) | No | Validated media content type |
| byte_size | BIGINT | Yes | Nonnegative size in bytes, if known |
| sha256 | CHAR(64) | Yes | Optional content-integrity digest |
| start_offset_seconds | NUMERIC(14,3) | Yes | Clip/frame offset from source start, when applicable |
| end_offset_seconds | NUMERIC(14,3) | Yes | End offset for a clip interval, when applicable |
| status | VARCHAR(24) | No | CHECK: processing, available, unavailable, failed |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign key: source_id references sources.id with deletion restricted.
- Unique: (storage_backend, storage_key).
- CHECK byte_size is NULL or byte_size >= 0.
- CHECK offsets are nonnegative when present.
- CHECK end_offset_seconds is NULL or start_offset_seconds is NULL or end_offset_seconds >= start_offset_seconds.
- A status of available means the referenced object was verified as available through the storage adapter; it does not mean the evidence proves the detection.
- Storage keys and filesystem paths must not be exposed to unauthorized clients.

### 4.8 incident_evidence

Links incidents to their evidence. This associative table allows more than one evidence item per incident and allows one source clip or asset to support multiple incidents without duplicating the media object.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| incident_id | UUID | No | FK to incidents.id |
| evidence_id | UUID | No | FK to evidence.id |
| association_role | VARCHAR(24) | No | CHECK: source_context, supporting, key_frame |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Composite primary key: (incident_id, evidence_id).
- Foreign keys reference incidents.id and evidence.id with deletion restricted.
- The backend must verify that evidence belongs to the expected source or is otherwise valid for that incident.
- Deleting an incident must not silently delete the underlying source video.

### 4.9 reliability_assessments

Stores versioned quality and evidence-sufficiency results for an incident.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| incident_id | UUID | No | FK to incidents.id |
| assessment_version | VARCHAR(120) | No | Version of the assessment logic/configuration |
| assessment_status | VARCHAR(24) | No | CHECK: completed, failed |
| evidence_sufficiency | VARCHAR(24) | Yes | CHECK: sufficient, insufficient, unknown |
| uncertainty_status | VARCHAR(24) | Yes | CHECK: not_uncertain, uncertain, abstained |
| measurements | JSONB | No | Default empty object; only actually computed measurements |
| reason_codes | JSONB | No | Default empty array of machine-readable reason codes |
| error_code | VARCHAR(80) | Yes | Safe code if assessment execution failed |
| assessed_at | TIMESTAMPTZ | Yes | Assessment completion time when available |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign key: incident_id references incidents.id with deletion restricted.
- CHECK measurements is a JSON object.
- CHECK reason_codes is a JSON array.
- If assessment_status is completed, assessed_at must be present.
- If assessment_status is failed, an appropriate error_code should be present.
- If assessment_status is failed, evidence_sufficiency and uncertainty_status should remain NULL rather than presenting a result that was not computed.
- The application must validate measurement names and meanings for the selected assessment version.
- Never treat video quality, detector confidence, anomaly score, and evidence sufficiency as interchangeable.

### 4.10 reviews

Stores human review decisions. Review records are append-oriented so the original decision history can be retained if a later review changes the outcome.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| incident_id | UUID | No | FK to incidents.id |
| reviewer_id | UUID | No | FK to users.id |
| outcome | VARCHAR(32) | No | CHECK: confirmed, false_alert, inconclusive |
| review_note | VARCHAR(2000) | Yes | Optional concise note |
| reviewed_at | TIMESTAMPTZ | No | Time the reviewer recorded the outcome |

**Constraints**

- Foreign keys: incident_id references incidents.id; reviewer_id references users.id. Deleting referenced rows should be restricted.
- Only authorized operators or supervisors may submit review outcomes.
- The reviewer must be active and authorized at submission time.
- Creating a review and updating incidents.review_status to reviewed must happen in one transaction.
- New review records must not overwrite detector-generated fields.
- Review history must not be deleted or edited by ordinary operators through the normal API. Corrections should be represented by a subsequent review record when history is enabled.

### 4.11 evaluation_assets

Represents individual video clips within a versioned evaluation dataset. This table is important for tracking eligible monitored duration and clips that contain no ground-truth incident.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| dataset_id | UUID | No | FK to evaluation_datasets.id |
| asset_key | VARCHAR(240) | No | Stable identifier within this dataset version |
| storage_backend | VARCHAR(24) | No | CHECK: local, object |
| media_storage_key | TEXT | No | Internal media-storage key |
| sha256 | CHAR(64) | Yes | Optional content-integrity digest |
| duration_seconds | NUMERIC(14,3) | Yes | Positive duration where known |
| eligible_for_metric_denominator | BOOLEAN | No | Default FALSE; include in monitored-hours denominator only when annotations and duration are complete |
| annotation_status | VARCHAR(24) | No | CHECK: complete, partial, unverified |
| availability_status | VARCHAR(24) | No | CHECK: available, unavailable, failed |
| condition_labels | JSONB | No | Default empty object, e.g. supported lighting/scene labels |

**Constraints**

- Foreign key: dataset_id references evaluation_datasets.id with deletion restricted.
- Unique: (dataset_id, asset_key).
- CHECK duration_seconds is NULL or duration_seconds > 0.
- CHECK condition_labels is a JSON object.
- If eligible_for_metric_denominator is TRUE, duration_seconds must be present and annotation_status must be complete.
- A clip with no ground-truth events is valid when its annotation status is complete; it can still contribute eligible video hours for false-alert-rate calculations.
- Dataset asset metadata and annotations used in a completed run must remain reproducible.

### 4.12 ground_truth_events

Stores independently annotated reference events for an evaluation asset.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| dataset_asset_id | UUID | No | FK to evaluation_assets.id |
| event_category | VARCHAR(120) | No | Reference event category |
| start_offset_seconds | NUMERIC(14,3) | No | Event start relative to the asset |
| end_offset_seconds | NUMERIC(14,3) | No | Event end relative to the asset |
| annotation_note | VARCHAR(1000) | Yes | Optional annotation clarification |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign key: dataset_asset_id references evaluation_assets.id with deletion restricted.
- CHECK start_offset_seconds >= 0.
- CHECK end_offset_seconds > start_offset_seconds.
- If asset duration is known, event end must not exceed the asset duration.
- Ground-truth annotations must be independently established; they must not be copied from detector predictions.
- Event-matching rules must define how overlapping predictions, category mismatches, and repeated detections are handled.

### 4.13 evaluation_runs

Represents one evaluation of a specific versioned dataset with a specific detector version and configuration.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| dataset_id | UUID | No | FK to evaluation_datasets.id |
| processing_job_id | UUID | No | FK to processing_jobs.id; unique one-to-one association |
| detector_name | VARCHAR(160) | No | Detector implementation identifier |
| detector_version | VARCHAR(120) | Yes | Model or code version |
| configuration | JSONB | No | Default empty object; thresholds and matching configuration used |
| status | VARCHAR(24) | No | CHECK: pending, running, completed, failed |
| eligible_asset_count | INTEGER | No | Default 0; nonnegative |
| excluded_asset_count | INTEGER | No | Default 0; nonnegative |
| failed_asset_count | INTEGER | No | Default 0; nonnegative |
| started_at | TIMESTAMPTZ | Yes | Evaluation start time |
| completed_at | TIMESTAMPTZ | Yes | Completion/final failure time |
| created_by | UUID | Yes | FK to users.id |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign keys: dataset_id references evaluation_datasets.id; processing_job_id references processing_jobs.id; created_by references users.id with ON DELETE SET NULL.
- Unique: processing_job_id.
- CHECK configuration is a JSON object.
- All sample counts must be nonnegative.
- A completed run must have completed_at.
- The linked processing job must be an evaluation job for the same dataset. Enforce this through application validation and integration tests; use a database-level constraint trigger only if later requirements justify the added complexity.
- Completed evaluation runs are immutable. A new detector version, dataset version, or configuration requires a new run.
- Configuration must not contain secrets or arbitrary private file paths.

### 4.14 metric_results

Stores calculated metrics for an evaluation run. Each metric result includes context sufficient to interpret its scope and availability.

| Column | Type | Nullable | Rules / purpose |
|---|---|---|---|
| id | UUID | No | Primary key |
| evaluation_run_id | UUID | No | FK to evaluation_runs.id |
| metric_key | VARCHAR(80) | No | Stable key, e.g. precision, recall, false_alerts_per_hour |
| scope_key | VARCHAR(200) | No | Default overall; identifies a documented condition breakdown where supported |
| availability_status | VARCHAR(24) | No | CHECK: available, unavailable, insufficient_data |
| value | NUMERIC(24,10) | Yes | Numeric result when available |
| unit | VARCHAR(80) | Yes | Unit, e.g. alerts/hour or seconds |
| numerator | NUMERIC(24,10) | Yes | Numerator where relevant |
| denominator | NUMERIC(24,10) | Yes | Denominator where relevant |
| sample_count | INTEGER | Yes | Nonnegative sample count |
| details | JSONB | No | Default empty object; supporting calculation details |
| unavailable_reason | VARCHAR(500) | Yes | Explanation when result is unavailable |
| created_at | TIMESTAMPTZ | No | Default current timestamp |

**Constraints**

- Foreign key: evaluation_run_id references evaluation_runs.id with deletion restricted.
- Unique: (evaluation_run_id, metric_key, scope_key).
- CHECK details is a JSON object.
- CHECK sample_count is NULL or sample_count >= 0.
- If availability_status is available, value must be present.
- If availability_status is unavailable or insufficient_data, value should be NULL.
- An undefined metric must not be written as zero.
- Keep metric definitions, units, denominators, and matching rules versioned/documented.
- For condition-specific results, scope_key must follow a documented canonical naming convention. Use an overall scope when no breakdown is applied.

## 5. Relationships and Delete Rules

### 5.1 Core Relationships

- One user may have multiple sessions.
- One user may create multiple sources, jobs, datasets, or reviews.
- One source may produce many incidents and contain multiple evidence objects.
- One incident may reference multiple evidence objects via incident_evidence.
- One incident may have multiple reliability assessments and reviews.
- One dataset version may contain many evaluation assets and reference events.
- One dataset version may be evaluated by multiple runs.
- One run may produce multiple metric results.
- One processing job may produce many incidents or be linked to one evaluation run.

### 5.2 Deletion Policy

Use restrictive deletion behavior for records with audit, evidence, or evaluation dependencies.

- Deactivate user accounts rather than deleting them.
- Do not hard-delete incidents that are needed to preserve review history.
- Do not cascade-delete original video when an incident or link is removed.
- Treat a dataset version used by a completed run as immutable.
- Media deletion must be performed through an explicit retention/cleanup procedure that updates database metadata consistently.
- Any approved privacy-driven erasure must follow a documented process, including its impact on audit records and evaluation reproducibility.

Avoid broad ON DELETE CASCADE relationships for evidence and history tables.

## 6. Constraints and Validation

### 6.1 Database-Enforced Rules

Use database constraints for rules that must remain true regardless of which application path writes the data:

- Primary-key and foreign-key integrity.
- Required fields and defaults.
- Unique normalized user email.
- Unique non-null source event identity per source.
- Valid role, state, and outcome values.
- Nonnegative file sizes, attempt counts, metric sample counts, and durations.
- Valid event and clip time intervals.
- JSONB object/array shape for fields defined to have a specific structure.
- Unique dataset name and version.
- Unique metric key and scope per evaluation run.
- Unique media storage backend and storage key.
- Required job target for each job type.

### 6.2 Application-Level Rules

Enforce in the application because they require user context, configuration, or multi-record logic:

- Email syntax and password policy.
- Password hashing and session lifecycle.
- Role and resource authorization.
- Source/evidence consistency for an incident.
- Whether a dataset is complete and permitted for a requested evaluation.
- Whether a requested detector/version is actually installed.
- Whether a media format can be processed.
- Whether a completed evaluation has sufficient valid inputs.
- Updating incident review_status with review creation.
- Keeping the job and evaluation run dataset references consistent.
- Whether an assessment threshold or metric definition is approved for use.

### 6.3 Validation Boundaries

Validate input at more than one layer where necessary:

1. Pydantic validates HTTP payload shape and input ranges.
2. Application services validate business rules.
3. PostgreSQL constraints enforce persistent invariants.

Client-side validation improves usability but is never the security boundary.

### 6.4 Prediction Immutability

Normal review APIs must not modify original detector fields after creation.

When new detector output is generated, create a new incident or a separately versioned prediction representation according to the approved reprocessing workflow. Do not overwrite historical outcomes silently.

## 7. Indexes Based on Actual Queries

Indexes should support the queries required by the product, not speculative scale.

| Table | Index / constraint | Query supported |
|---|---|---|
| users | UNIQUE(email) | Login and account lookup |
| sessions | UNIQUE(token_hash) | Resolve authenticated session |
| sessions | (user_id, expires_at) | List/revoke sessions and clean expired sessions |
| sources | (status, created_at DESC) | System-status view |
| sources | (created_by, created_at DESC) | Administrative source listing where used |
| processing_jobs | Partial index on (available_at, created_at) WHERE status = pending | Worker job claiming |
| processing_jobs | (status, heartbeat_at) | Inspect running and potentially abandoned jobs |
| processing_jobs | (source_id, created_at DESC) | Source processing history where shown |
| incidents | (received_at DESC) | Recent incident list/order |
| incidents | (review_status, received_at DESC) | Unreviewed/reviewed queue |
| incidents | (source_id, event_start_at DESC) | Incidents from a source over time |
| incidents | (detection_category, received_at DESC) | Category-filtered incident lists where used |
| incidents | Partial UNIQUE(source_id, source_event_id) WHERE source_event_id IS NOT NULL | Idempotent detection ingestion |
| evidence | UNIQUE(storage_backend, storage_key) | Prevent duplicate storage references |
| evidence | (source_id, created_at DESC) | Evidence for a source |
| incident_evidence | PRIMARY KEY(incident_id, evidence_id) | Evidence for an incident |
| incident_evidence | (evidence_id, incident_id) | Find incident associations for an evidence object |
| reliability_assessments | (incident_id, assessed_at DESC) | Latest or historical assessments for an incident |
| reviews | (incident_id, reviewed_at DESC) | Review history for an incident |
| reviews | (reviewer_id, reviewed_at DESC) | Reviewer activity when required |
| evaluation_datasets | UNIQUE(name, version) | Dataset version lookup |
| evaluation_assets | UNIQUE(dataset_id, asset_key) | Assets within a dataset |
| ground_truth_events | (dataset_asset_id, start_offset_seconds) | Load annotations in event-time order |
| evaluation_runs | (dataset_id, created_at DESC) | Evaluation history for a dataset |
| evaluation_runs | UNIQUE(processing_job_id) | Resolve an evaluation from its job |
| metric_results | UNIQUE(evaluation_run_id, metric_key, scope_key) | Retrieve a metric and prevent duplicate metric rows |

### 7.1 Indexing Rules

- PostgreSQL automatically indexes primary keys and unique constraints; do not create duplicates.
- The pending-job index should be partial so completed jobs do not burden the queue-claim query.
- Start with the indexes above only where the corresponding query is implemented.
- Validate query plans on realistic fixture data before adding composite indexes.
- Do not add GIN indexes to all JSONB columns. Add one only if an implemented query filters within that JSON structure frequently enough to justify it.
- Revisit indexes when the query patterns or measured workload change.

## 8. Ownership and Authorization

### 8.1 Application as Authorization Boundary

For the single-institution MVP, the backend application is responsible for authorization.

Every endpoint that accesses an incident, evidence item, source, evaluation, or processing job must:

1. Authenticate the current user.
2. Check the role required for the operation.
3. Load the resource through an authorized query or verify its access scope.
4. Return only the fields and evidence the user is permitted to access.

Do not rely on obscured IDs, frontend route guards, or hidden buttons for security.

### 8.2 Ownership Columns

The following ownership references support auditability and controlled administration:

- sources.created_by.
- processing_jobs.created_by.
- evaluation_datasets.created_by.
- evaluation_runs.created_by.
- reviews.reviewer_id.

A source, dataset, incident, or evidence record is not private solely because it has a creator. Access rules should follow the PRD's institutional roles, not assume that only its creator may view it.

### 8.3 Row-Level Security (RLS)

**MVP decision: PostgreSQL RLS is not required for the initial single-institution deployment.**

Reasons:

- There is no approved multi-tenant organization model in the PRD.
- The application already needs explicit role- and resource-level authorization.
- Adding RLS without a tenant boundary would duplicate access logic without a clear isolation requirement.

Application-level authorization is still mandatory and must be tested through direct API requests.

### 8.4 Future Multi-Tenant Requirement

Before serving multiple independent institutions:

- Introduce an organizations/tenants table only when the product requirement is approved.
- Add tenant ownership to each tenant-scoped record and enforce consistent ownership across foreign-key relationships.
- Apply tenant scoping to every repository query.
- Evaluate PostgreSQL RLS as defense in depth.
- Set tenant context transaction-locally and ensure it cannot leak across pooled connections.
- Test cross-tenant access through both API tests and direct database-policy tests.
- Ensure background workers set and validate the appropriate tenant context.
- Do not treat the current single-institution schema as automatically tenant-safe.

## 9. Sensitive-Data Handling

### 9.1 Credentials and Sessions

- Store only a strong password hash, never a password.
- Store only a hash of the session token.
- Never write credentials or session tokens into logs.
- Invalidate sessions for disabled users.
- Use secure cookie settings and CSRF protection as defined in ARCHITECTURE.md.

### 9.2 Video and Evidence

- Keep media bytes outside PostgreSQL.
- Keep real video outside public web directories.
- Store opaque internal storage keys rather than public filesystem paths.
- Restrict media access through the backend or tightly scoped short-lived signed URLs if object storage is later adopted.
- Do not place private footage, extracted frames, or large model weights in Git.
- Record only the metadata needed for evidence integrity, review, processing, and retention.
- Do not send video to external AI providers unless explicitly approved.

### 9.3 JSONB Fields

JSONB fields such as source configuration, measurements, condition labels, and evaluation configuration must contain validated, non-secret data.

Do not use JSONB as an unbounded dumping ground for raw requests, arbitrary detector payloads, credentials, or private filesystem paths.

### 9.4 Logs and Diagnostics

- Keep error summaries sanitized.
- Never log raw request cookies, passwords, or session tokens.
- Do not log video contents or frame data.
- Avoid unnecessary personal data in processing diagnostics.
- Use request and job identifiers to correlate failures instead of duplicating sensitive inputs in logs.

### 9.5 Retention

The exact retention period for video and related metadata requires approval under the product's privacy and institutional requirements.

The implementation must support a documented retention procedure without silently deleting data that is still required for an active review or valid evaluation run.

## 10. Migration Strategy

### 10.1 Tooling

Use Alembic migrations alongside SQLAlchemy models.

Every schema change must include a migration reviewed into version control.

### 10.2 Initial Migration Order

Create tables in an order that respects foreign keys:

1. users
2. sources
3. evaluation_datasets
4. processing_jobs
5. incidents
6. evidence
7. incident_evidence
8. reliability_assessments
9. reviews
10. evaluation_assets
11. ground_truth_events
12. evaluation_runs
13. metric_results
14. Required secondary indexes and partial indexes

Where an implementation's migration framework requires a different order, arrange migrations to avoid unresolved foreign-key dependencies.

### 10.3 Migration Rules

- Do not edit an already-applied production migration.
- Create a new migration for changes to an existing schema.
- Review generated migrations rather than trusting automatic generation alone.
- Test migrations against an empty database and a representative existing database.
- Prefer additive, backward-compatible changes where possible.
- Avoid destructive column or table removal without a documented data-migration and rollback plan.
- Do not run destructive migrations automatically during web application startup.
- Treat dataset versions and completed evaluation results as immutable historical records.

### 10.4 Schema Ownership

SQLAlchemy models define application mappings. Alembic migrations define how the database evolves.

Changes to models without corresponding migrations are incomplete.

## 11. Seed and Fixture Strategy

### 11.1 Demo Users

A seed command may create a minimal set of operator, supervisor, and technical-administrator users.

- Obtain demo passwords from environment configuration or an interactive setup step.
- Never commit actual credentials.
- Hash credentials using the configured password-hashing implementation.
- Make the command idempotent.
- Do not automatically create demonstration accounts in production.

### 11.2 Demonstration Sources and Incidents

Seed only the number of sources and incident records needed to demonstrate the user journeys.

- Label simulated sources explicitly.
- Use deterministic identifiers where they simplify reproducible tests.
- Set the detector name/version to a clear simulated identifier for sample predictions.
- Include examples of sufficient evidence, uncertain evidence, missing evidence, and a processing failure only when those states are accurately represented.
- Do not portray synthetic records as actual campus events.

### 11.3 Evaluation Fixtures

Use small, deterministic, appropriately licensed test fixtures with independently prepared ground-truth annotations.

Tests must include:
- A clip with a labeled event.
- A clip with no events but complete annotations.
- A false-positive prediction case.
- A missed-event case.
- An unavailable or failed asset case.
- A case where a metric is undefined.

Expected metrics must be independently calculated and fixed in tests.

### 11.4 Seed Separation

Keep these distinct:

- Schema migrations.
- Demo-data seeding.
- Automated-test fixtures.
- Actual uploaded video and evaluation data.

Do not mix test fixtures into real evaluation datasets without clear provenance and explicit approval.

## 12. Backup and Recovery

### 12.1 What Must Be Backed Up

A complete recovery plan must account for both:

1. PostgreSQL data, including users, incident metadata, reviews, assessments, processing state, dataset annotations, and evaluation results.
2. Video and evidence objects stored outside PostgreSQL.

Backing up only the database is insufficient if its evidence references point to missing media. Backing up only video files is insufficient if the incident and review records are lost.

### 12.2 Database Backups

For a shared or production deployment:

- Use managed PostgreSQL backups or a documented PostgreSQL backup process.
- Encrypt backups at rest and restrict their access.
- Protect backup credentials separately from application credentials.
- Establish a retention policy appropriate to the permitted data and storage budget.
- Monitor backup success and failure.
- Keep backups isolated from routine application write permissions.

For local development, a database dump may be sufficient.

### 12.3 Evidence Backups

- Back up the private storage location or use a storage service with an approved durability and recovery policy.
- Preserve storage keys and content checksums.
- Protect video backups with access controls equivalent to the original media.
- Coordinate database and media recovery using backup timestamps, manifests, or versioned objects.
- Document how to identify database references whose media is missing.

### 12.4 Restore Testing

A backup is not accepted as reliable until restoration has been tested.

Recovery checks should verify:

- Users and sessions are restored appropriately; active sessions may be intentionally invalidated.
- Incidents and review history remain consistent.
- Foreign-key and uniqueness constraints hold.
- Evidence references resolve to the expected objects.
- Checksums match where available.
- Evaluation runs and metric results preserve their source versions.
- Processing jobs left running at backup time can be safely reconciled or requeued.

### 12.5 Recovery Targets

The target recovery point objective (RPO) and recovery time objective (RTO) require approval based on the deployment environment and operational importance.

Do not claim zero data loss or a specific recovery time unless it has been designed, tested, and supported by the hosting arrangement.

## 13. Operational Data Integrity Rules

The following invariants must hold throughout the application's life:

1. Every incident has a valid source.
2. A repeated source event cannot create duplicate incidents when a stable source-event ID exists.
3. Every incident prediction retains its original detector name, version, label, and score semantics.
4. An incident may link to multiple evidence items without duplicating media bytes.
5. Every completed reliability assessment identifies its version and assessment time.
6. A failed assessment does not masquerade as an uncertain result that was successfully computed.
7. Every saved review identifies a reviewer, outcome, and timestamp.
8. Creating a review and updating the incident's review status are one logical transaction.
9. Every completed evaluation identifies its dataset version, detector version, and configuration.
10. Ground-truth events are independent of predictions under evaluation.
11. Metric values are either available with documented context or explicitly unavailable.
12. Media objects are not publicly reachable by default.
13. Hard deletion does not accidentally erase review or evaluation history.
14. Simulated data remains identifiable as simulated throughout source, incident, and evaluation views.

## 14. Database Acceptance Criteria

The database implementation is complete when:

- [ ] All required entities and relationships exist.
- [ ] Primary keys, foreign keys, uniqueness constraints, and CHECK constraints are implemented.
- [ ] Migrations can create a clean database from scratch.
- [ ] Email, password, and session data follow the sensitive-data requirements.
- [ ] Source-event deduplication is enforced where stable IDs are available.
- [ ] Incident-to-evidence associations preserve source integrity.
- [ ] Predictions remain distinct from assessments and human review outcomes.
- [ ] Processing jobs can be claimed and recovered without duplicate output records.
- [ ] Versioned datasets and ground-truth event intervals support evaluation.
- [ ] Metric results preserve scope, units, denominators, and unavailable states.
- [ ] Indexes cover the actual incident, review, evidence, and job queries.
- [ ] Application-level role and resource authorization is tested.
- [ ] Sensitive evidence is stored outside public application assets.
- [ ] Seed operations are idempotent and do not introduce production credentials.
- [ ] Backup and restore procedures cover both database records and evidence media.
- [ ] Test cases verify transaction integrity, migrations, metric correctness, and failure handling.

## 15. Final Database Definition

SafeCity AI uses PostgreSQL as the authoritative store for application identities, sources, incidents, evidence metadata, reliability assessments, reviews, processing jobs, evaluation datasets, annotations, and metric results.

Media bytes remain in private storage. Background processing is represented explicitly through jobs. Evaluation results retain their dataset and detector context. Human review does not overwrite the original model prediction.

The MVP uses application-enforced resource authorization for a single institution. Row-level security and tenant-specific schema fields are deferred until a multi-tenant product requirement is approved.

The schema deliberately avoids premature infrastructure and speculative data entities while preserving the integrity required for reliable incident review and measurable model evaluation.

**The defining database principle is simple: preserve evidence provenance, maintain a clear history of machine and human decisions, and ensure every reported metric can be traced back to the data that produced it.**
